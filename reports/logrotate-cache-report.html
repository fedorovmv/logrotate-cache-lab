File cache при ротации логов Envoy

Сравнение copytruncate из текущего pilot-agent и rename + reopen на disk-backed storage под cgroup memory limit.

30 июля 2026 Docker Desktop / Linux VM C++ writer tmpfs исключён 3 повтора на границе файлы 50 и 100 MiB
Вывод: размер ротируемого файла влияет на минимальный лимит нелинейно. Для copytruncate устойчивая граница выросла с 68 MiB при файле 50 MiB до 72 MiB при 100 MiB, а не ещё на 50 MiB. Rename + reopen и baseline с файлом 100 MiB прошли при 56 MiB. Пять copytruncate-ротаций по 50 MiB также прошли при 68 MiB: повторное копирование не аккумулировало обязательный RAM minimum, потому что cgroup reclaim вытеснял старые clean file pages.
Что означает «минимальный limit»? Это наименьший проверенный Docker --memory / cgroup memory.max, при котором прошли все три запуска; соседний кандидат на 4 MiB ниже не прошёл. В limit входят 32 MiB эмулируемого resident working set, C++ writer, Go run/monitor/rotator, anonymous memory, file cache, dirty и writeback pages. Это граница стенда в данной Linux VM, а не требование настоящего Envoy и не размер кеша.

При высоком limit cache может достигать размера всех retained-файлов. Под жёстким limit ядро не обязано держать их в RAM: clean file pages reclaimable. Поэтому 5 × 50 MiB backup-файлов занимают 250 MiB на диске, но успешный copytruncate container limit остался 68 MiB.

Почему раньше в отчёте было 88 MiB? Первый широкий sweep 32–192 MiB действительно дал 84 fail / 88 pass для copytruncate 50 MiB. Более поздние side-by-side pressure-прогоны дали 64 fail / 68 pass. Near-OOM граница зависит от scheduling reclaim/writeback и состояния Linux VM. Поэтому 88 MiB сохранено как результат старого прогона, но не используется как универсальный minimum; итоговая таблица опирается на одинаково настроенные соседние кандидаты и показывает число успешных повторов.

Потеря у copytruncate возникает, когда writer сбрасывает buffered block после того, как копирование дошло до EOF, но до truncate. fsync backup-файла делает уже скопированные данные устойчивыми, однако не закрывает это окно. Точное число зависит от scheduling и момента flush, но на 50 MiB проблема воспроизвелась во всех трёх минимальных успешных попытках.

Ответ про аккумуляцию. Cache retained backup-файлов накапливается у обеих стратегий примерно по 50 MiB за ротацию, пока ядро не испытывает memory pressure. Copytruncate не оставляет постоянную вторую копию каждой ротации в cache: после truncate лишние страницы active inode уходят. Но при каждом следующем копировании появляется transient ещё на один полный файл, поэтому пила растёт как retained backups + 50 MiB. Rename/reopen растёт почти линейно без этих дополнительных зубцов.

Почему minimum не равен размеру копируемого файла

Copytruncate читает и записывает файл потоком. Пока новые страницы входят в cache, Linux параллельно выполняет writeback и reclaim старых clean pages. OOM определяется максимальным одновременным невытесняемым окном, а не суммой размеров файлов на диске. Удвоение файла с 50 до 100 MiB удлинило время, в течение которого copy конкурирует за память, и подняло проверенную границу на 4 MiB, но не потребовало держать дополнительные 50 MiB resident.

Устойчивый результат этого стенда — форма зависимости: copytruncate требует дополнительного headroom и даёт transient-пилу; rename + reopen остаётся близко к baseline. Production sizing нужно повторить на целевом kernel/storage и с реальным Envoy.

Влияние реализации writer

Первый вариант использовал Go writer, и его GC/runtime заметно влиял на минимальный лимит. Docker/kind writer был переписан на C++17: фиксированный record buffer, предварительно зарезервированный flush buffer, отсутствие сборщика мусора.

RSS снимался через docker top в диагностическом запуске. Суммировать RSS процессов как cgroup memory нельзя: общие file-backed страницы могут учитываться в RSS нескольких процессов. Для cgroup-анализа отчёт использует memory.current, memory.stat anon и memory.stat file.

Методика

Memory boundary

  • Файлы: 50 и 100 MiB
  • Ротации: 1 и 5; для серии max-backups=5
  • Поток: 8 MiB/s, record 512 B
  • Buffer: 64 KiB, flush 100 ms
  • Resident allocation: 32 MiB
  • Pressure-кандидаты: соседние limits, шаг 4 MiB
  • Три повтора каждого кандидата
  • --memory-swap == --memory

Изоляция и наблюдение

  • Свежий Docker local volume на попытку
  • Disk-backed storage, без tmpfs
  • C++ writer и Go rotator — разные процессы
  • Cgroup v2 memory/file/anon counters
  • Exit 137 и child-only OOM распознаются отдельно
  • Sequence-ID integrity по active + backups
  • Accumulation profile: 5 × 50 MiB, max-backups=5, sampling 20 ms

Ограничения

  1. Это сравнительный стенд, не sizing настоящего Envoy. C++ writer не воспроизводит allocator, worker threads и полную access-log реализацию Envoy.
  2. Числа получены внутри Linux VM Docker Desktop. Production kernel, filesystem, cgroup и storage class могут изменить reclaim/writeback.
  3. Проверены 50 и 100 MiB и серия из пяти ротаций. Это не доказывает ту же численную границу для иных размеров, write rate или числа backup-файлов.
  4. График пяти ротаций снят при высоком лимите 768 MiB, поэтому показывает накопление без активного cgroup reclaim. Под жёстким production limit старые clean cache pages могут вытесняться раньше.
  5. Baseline содержит обычную запись того же объёма и служит reference, но не является строгой нижней границей.
  6. Потеря copytruncate зависит от scheduling и flush timing; отсутствие потери в одном запуске не доказывает безопасность алгоритма.

Рекомендация

Реализовать в pilot-agent ротацию rename → создать replacement → вызвать Envoy /reopen_logs. Старый inode остаётся доступен writer до обработки reopen, поэтому данные в переходном окне попадают в переименованный backup. Перед rollout выполнить тот же трёхкратный sweep с реальным Envoy, production-размером лог-файла и целевым memory limit.
