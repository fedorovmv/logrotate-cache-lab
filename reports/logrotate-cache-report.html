File cache при ротации логов Envoy

Сравнение copytruncate из текущего pilot-agent и rename + reopen на disk-backed storage под cgroup memory limit.

30 июля 2026 Docker Desktop / Linux VM C++ writer tmpfs исключён 3 повтора на границе
Вывод: для протестированного workload вариант rename + reopen является предпочтительным. Он исключает полнофайловое копирование, прошёл на лимите 24 MiB против 32 MiB у copytruncate и сохранил все sequence ID. Copytruncate требует дополнительный запас памяти и имеет неустранимое окно потери записей между достижением EOF при копировании и truncate.

Почему rename ниже baseline? Baseline — контрольный workload с тем же объёмом обычной записи в один растущий inode, а не теоретическая нижняя граница. Rename меняет жизненный цикл inode и условия reclaim; кроме того, граница дискретна и чувствительна к планированию/writeback. Корректная прямая величина для выбора алгоритма здесь — 32 против 24 MiB. Отрицательная delta не означает «отрицательное потребление памяти».

Потеря у copytruncate не обязана происходить в каждом коротком запуске. Она возникает, когда writer сбрасывает buffered block после того, как копирование дошло до EOF, но до truncate. fsync backup-файла делает уже скопированные данные устойчивыми, однако не закрывает это окно.

На коротком 4 MiB workload headline cache-fill почти одинаков: его задаёт основной поток записи 8 MiB/s. Копирование — короткий transient, который монитор с интервалом 100 ms может не поймать целиком. Поэтому для memory headroom более показателен повторный OOM boundary test. На production-размере 32–100 MiB следует повторить тест с интервалом 20–50 ms.

Влияние реализации writer

Первый вариант использовал Go writer, и его GC/runtime заметно влиял на минимальный лимит. Docker/kind writer был переписан на C++17: фиксированный record buffer, предварительно зарезервированный flush buffer, отсутствие сборщика мусора.

RSS снимался через docker top в диагностическом запуске. Суммировать RSS процессов как cgroup memory нельзя: общие file-backed страницы могут учитываться в RSS нескольких процессов. Для cgroup-анализа отчёт использует memory.current, memory.stat anon и memory.stat file.

Методика

Memory boundary

  • Файл: 4 MiB, одна ротация
  • Поток: 8 MiB/s, record 512 B
  • Buffer: 64 KiB, flush 100 ms
  • Resident allocation: 8 MiB
  • Диапазон: 16–64 MiB, шаг 4 MiB
  • Три повтора каждого кандидата
  • --memory-swap == --memory

Изоляция и наблюдение

  • Свежий Docker local volume на попытку
  • Disk-backed storage, без tmpfs
  • C++ writer и Go rotator — разные процессы
  • Cgroup v2 memory/file/anon counters
  • Exit 137 и child-only OOM распознаются отдельно
  • Sequence-ID integrity по active + backups

Ограничения

  1. Это сравнительный стенд, не sizing настоящего Envoy. C++ writer не воспроизводит allocator, worker threads и полную access-log реализацию Envoy.
  2. Числа получены внутри Linux VM Docker Desktop. Production kernel, filesystem, cgroup и storage class могут изменить reclaim/writeback.
  3. Файл 4 MiB выбран для быстрого устойчивого теста. При 32–100 MiB стоимость copytruncate должна измеряться повторно.
  4. Baseline содержит обычную запись того же объёма и служит reference, но не является строгой нижней границей.
  5. Потеря copytruncate зависит от scheduling и flush timing; отсутствие потери в одном запуске не доказывает безопасность алгоритма.

Рекомендация

Реализовать в pilot-agent ротацию rename → создать replacement → вызвать Envoy /reopen_logs. Старый inode остаётся доступен writer до обработки reopen, поэтому данные в переходном окне попадают в переименованный backup. Перед rollout выполнить тот же трёхкратный sweep с реальным Envoy, production-размером лог-файла и целевым memory limit.
