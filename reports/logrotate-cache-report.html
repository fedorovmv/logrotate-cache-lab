Ротация логов Envoy

Влияние copytruncate и rename + reopen на файловый кеш, лимит памяти контейнера и целостность логов.

Docker Desktop / Linux 6.10.14 дисковый Docker volume эмулятор Envoy на C++17 файлы 50 и 100 MiB 3 запуска на значение

Copytruncate копирует активный лог в новый файл и затем обрезает исходный. При свободной памяти это почти удваивает скорость роста файлового кеша и создаёт дополнительный пик примерно на размер лог-файла. Алгоритм также теряет записи, сделанные между окончанием копирования и обрезанием исходного файла.

Rename + reopen переименовывает активный файл и переключает Envoy на новый. В выполненных тестах его потребление памяти совпало с обычной записью без ротации; потери записей не обнаружены.

Влияние размера файла не установлено. Для 50 MiB получено 68 MiB, для 100 MiB — 72 MiB. Разница равна одному шагу теста, а граница OOM заметно менялась между сериями запусков. Эти данные не доказывают рост потребления памяти при увеличении файла. Они показывают только отсутствие пропорционального роста на полный размер файла в данной серии.

Файловый кеш при лимите 768 MiB

Пять ротаций файлов по 50 MiB выполнялись при лимите 768 MiB. Ядру не требовалось освобождать кеш из-за нехватки памяти.

Между ротациями обе линии растут с одной и той же скоростью — около 8 MiB/s, то есть со скоростью writer. Copytruncate отличается не наклоном линии, а короткими вертикальными скачками во время копирования: к кешу добавляется ещё около 47,6 MiB. После обрезания исходного файла этот объём исчезает. Постоянного удвоения кеша после каждой ротации не наблюдалось.

Пять резервных файлов занимали 250 MiB на диске, но файловый кеш copytruncate при лимите 68 MiB не превышал 19,2 MiB. Следовательно, сохранённые файлы не резервируют равный объём оперативной памяти: при нехватке памяти Linux освобождает часть файлового кеша.

Причина расхождения 68 и 72 MiB не доказана. Копирование выполнялось через copy_file_range, без пользовательского буфера размером с файл. Вероятное объяснение ограниченного кеша — запись и освобождение уже обработанных страниц во время копирования. Счётчики непосредственного сканирования и вытеснения страниц (pgscan/pgsteal) не записывались, поэтому вклад ядра, файловой системы и скорости диска разделить нельзя.

Во всех выполненных проверках отсутствующие, повторяющиеся и повреждённые записи не обнаружены.

Потери copytruncate вызваны порядком операций, а не лимитом памяти. Envoy продолжает писать в активный файл во время его копирования. Записи, добавленные после достижения конца файла копирующим процессом, но до последующего обрезания файла, отсутствуют и в резервной копии, и в новом активном логе. fsync сохраняет уже скопированные данные, но не устраняет это окно.

Выводы

  1. Copytruncate добавляет полный проход чтения и записи по лог-файлу. При достаточном лимите памяти это увеличило пик файлового кеша с 49,8 до 100,4 MiB для файла 50 MiB.
  2. При пяти ротациях copytruncate создавал временный пик на размер одного дополнительного файла, но не оставлял постоянную вторую копию каждой ротации в кеше.
  3. При малом лимите Linux удерживал в кеше только часть сохранённых файлов. Пять файлов по 50 MiB не увеличили проверенный лимит copytruncate выше 68 MiB.
  4. Дополнительный пик и дополнительный запас памяти — разные величины. В этом тесте пик copytruncate достигал примерно 48 MiB, но проверенный рабочий лимит был выше rename + reopen на 12–16 MiB: большую часть пика Linux успевал вытеснить. Эти 12–16 MiB несущественны при большом запасе памяти, но могут быть критичны для контейнера, уже работающего у границы OOM.
  5. Зависимость минимального лимита от размера файла не установлена: разница между 68 и 72 MiB равна шагу измерения.
  6. Copytruncate терял записи при всех проверенных лимитах. Rename + reopen потерь не показал и по памяти совпал с обычной записью без ротации.

Рекомендация

Заменить copytruncate в pilot-agent на последовательность переименовать активный файл → создать новый пустой файл → вызвать Envoy /reopen_logs. Перед внедрением повторить тест с настоящим Envoy на целевой версии ядра, файловой системе и storage class. Абсолютные лимиты 56–72 MiB относятся только к тестовому контейнеру и не являются рекомендацией для production.
Методика и ограничения
  • Эмулятор Envoy — отдельный процесс на C++17; pilot-agent, сборщик метрик и управляющий процесс — на Go.
  • Скорость записи — 8 MiB/s; запись — 512 байт; буфер — 64 KiB; сброс — не реже 100 ms.
  • Дополнительная постоянно используемая память — 32 MiB.
  • Для каждого запуска создавался новый дисковый Docker volume; tmpfs не использовался.
  • Стенд сравнивает алгоритмы, но не воспроизводит allocator, рабочие потоки и access log настоящего Envoy.
  • Первый широкий прогон copytruncate 50 MiB дал 88 MiB, повторная серия — 68 MiB. Граница OOM зависит от состояния Linux VM и не воспроизводилась между сериями как абсолютное значение.
  • Для доказательства влияния размера файла нужны меньший шаг, больше повторов и чередование запусков разных размеров.
